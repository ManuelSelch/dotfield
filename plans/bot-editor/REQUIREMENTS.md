# Visual Enemy Logic Editor MVP — Requirements

## Goal
Let a player visually edit an enemy's strategy, save it locally, and play a new match against it. Replace handwritten block-editing mechanics with Blockly while preserving Dotfield's simple, Scratch-inspired interaction style and the existing persistent behavior-tree agent.

Confirmed MVP scope includes reusable tactics with parameters and custom logic available in normal Home settings. This is an implementation plan, not authorization to implement. The [visual mockup](../../mockups/bot-editor/DESIGN.md) received positive UX feedback, but its illustrative functions and MDSL view are not implemented contracts. The approved [capture prototype](../../docs/ai-mdsl/IMPLEMENTATION.md) remains the gameplay baseline.

## Scope
### In Scope
- An isolated Blockly feasibility/design check before production integration, using the Scratch-inspired Zelos renderer and Dotfield colors.
- One Main entry plus editable, named reusable tactics with typed input parameters per enemy project. Seed Main with Capture(neutral) followed by Capture(enemy), sharing the current tree-authored multi-source capture tactic.
- Nested flow blocks, inline arguments, add/move/delete, undo/redo, useful error messages and a mobile/keyboard-accessible editing flow.
- Explicit local Save, Reset to default, and discard/cancel handling for unsaved changes.
- A versioned Blockly project as the editable source; validated Mistreevous JSON as the generated execution format.
- An explicit Normal/Custom logic choice per configured enemy in normal Home settings, without requiring a development URL flag; immutable strategy snapshots for new matches, replay and restored rounds.
- Existing agent capabilities and simulation-time lifecycle, not a new AI implementation.
- Shared-definition tabs, tactic creation/rename/deletion, parameter editing, call blocks and bounded compilation of reusable tactics into native behavior-tree definitions.

### Out of Scope
- A public/shared tactic library, recursion, return values, arbitrary parameter expressions, mutable parameter references and passing city/list/set/plan memory slots between tactics. MVP parameters are typed scalar inputs, not a general-purpose function language.
- Editable MDSL, arbitrary MDSL import, lossless block/text round-tripping or a custom general-purpose language. A text export is optional follow-up work, not an MVP dependency.
- JavaScript execution, arbitrary method names, arbitrary user plugins, uploaded code or third-party/shared bot projects.
- Live editing during a round, hot-swapping active plans, runtime memory serialization and a live execution debugger/highlighting UI.
- New tactics, defense capabilities, city-candidate iteration, coordinated arrival timing, aircraft, conversion or changes to combat rules.
- A generic variable/type-programming environment, general worker migration, online accounts, cloud storage and sharing/import/export UI.
- Replacement of the existing utility AI or claims that custom bots are competitively balanced.

## Requirements
- **Entry and activation:** provide Edit logic within each enemy's Home settings. Normal keeps the existing AI behavior selection and utility-AI path. Custom uses that enemy's valid saved project. Inactive enemy projects remain stored without executing. Existing behavior presets continue to supply scheduling where applicable; their utility-scoring preferences must not be presented as controlling a custom tree. Custom logic is available in normal production Home settings; development-only exposure is not the MVP delivery target.
- **Design approval:** retain the existing light visual language, compact library and nested C-shaped blocks. Validate the actual Blockly interaction rather than promising pixel-identical reproduction of the handwritten mockup. Obtain explicit approval of the Blockly-backed revision and verify/stop its owned mockup server before production implementation. Do not treat the request for this plan as that approval.
- **Small initial language:** support one Main entry, named tactic definitions/calls with typed input parameters, selector, sequence and bounded retry; SelectCity, SelectSources, NextCity, ClearSet, AddToSet, PlanCapture and ExecutePlan. Provide explicit sequence cleanup mapped to ReleasePlan on success/failure/abort, with cleanup visible in the UI. Do not expose arbitrary callback entry/step code or unrestricted Blockly programming blocks. Other nodes such as waits and custom guards are deferred.
- **Primitive policy boundary:** the tree chooses target class, branch order, source accumulation and retry limits. PlanCapture forecasts exactly the supplied ordered source set; ExecutePlan tracks and executes it. Neither the compiler nor the agent may silently add donors, search alternate subsets, select a different target or insert a new fallback strategy.
- **Editable fields:** support the existing neutral/enemy query, nearest-reachable ranking, minimum dispatchable army, bounded retry attempts, forecast duration, and a small set of named typed memory slots. Slot selection must distinguish city, source-list, chosen-set and capture-plan values; avoid making players type method names or JSON. Invalid combinations must be explained rather than silently repaired. Initialize the default tree with isolated neutral/attack slots as in the current prototype.
- **Reusable tactics:** players can create, rename and delete a named tactic, declare its named typed scalar inputs, edit its shared body in a tab and call it from Main or another tactic. Initial input types cover the existing query/ranking enums and bounded numeric fields. Calls supply literals or forward a parameter from the enclosing tactic; no arbitrary expressions, mutable arguments or return values. Parameter values are bound for that invocation, including across RUNNING ticks. Tactics propagate normal SUCCEEDED/FAILED/RUNNING results; calls are not fire-and-forget commands. The bundled Capture(kind) definition is shared by the neutral and enemy calls.
- **References and edits:** use stable tactic/parameter identities so renaming a definition or parameter preserves its references. Signature changes visibly invalidate missing/incompatible call arguments rather than silently substituting values. Prevent deletion of a referenced tactic until its calls are removed or explicitly resolved; undo restores the definition and references. Editing a shared definition updates every call at the next compilation, never a running match.
- **Editing:** players can add blocks from the library, nest supported groups, change arguments, navigate Main/tactic tabs, reorder/delete steps and undo/redo edits. Provide a usable touch and keyboard path for essential operations; do not assume desktop dragging alone satisfies the phone use case. Reparenting cannot introduce structural cycles. Explain that selector branches are tried in order and running plans retain their branch.
- **Single editable source:** persist a project envelope with a format version and Blockly workspace/procedure-model state for Main and all tactic definitions, including parameter signatures, stable definition/parameter/block IDs and editor information needed to restore the workspaces. Save/load must preserve behavior and visual editability. Persist neither editable MDSL nor a separately editable generated tree. Generated runtime JSON is derived, not a second authoring source. Unknown versions must not be silently coerced or overwritten.
- **Compiler:** compile supported workspace blocks directly into typed Mistreevous root/node definitions. Preserve child order, retry/decorator shape, authored action arguments and cleanup callbacks. No JavaScript generator, eval or text-parse intermediate is required. Keep serialization/validation/compiler code independent of React. Preserve block-to-runtime-node associations for errors and a future debugger without requiring live highlighting now. Compile reusable calls by bounded expansion with typed parameter substitution and deterministic call-site-local memory-slot prefixes. Each call site has separate local city/list/set/plan slots; nested calls cannot overwrite another invocation's memory. Re-entering a call follows normal fresh-attempt/cleanup behavior rather than allocating unbounded invocation memory. Cleanup arguments must receive the same slot binding as the actions they clean up; do not rename scalar literals as if they were memory references. Generated nodes retain both definition block IDs and call paths. Use Blockly's procedure data models where suitable; do not invent native MDSL function syntax or add a third general AST format.
- **Runtime equivalence:** the seeded visual project must behave like the existing capture tree: neutral priority, enemy fallback after bounded failures, explicit chosen-source accumulation, exact combined forecasting, one acknowledged order per source, normal decision cadence, persistent RUNNING execution and release of bot memory without recalling troops. Existing hand-authored MDSL remains usable through its separate development path. Extend the runtime definition input to accept native JSON; do not rewrite the agent.
- **Validation:** before activation, validate the versioned envelope, supported block types, one Main entry, named tactic definitions, connection shapes, required fields, finite numeric ranges, slot declarations/kinds and any structurally certain read-before-write errors. Reject missing tactic/parameter references, duplicate names in their scope, missing/extra/incompatible arguments and both direct and indirect recursion. Validate forwarded parameters and numeric constraints at each call site. Declared tactic roots are valid definitions, not dangling executable stacks. Empty executable groups, unsupported active blocks and dangling executable stacks must not be silently ignored; reject them with block-linked messages or explicitly mark excluded drafts. Ordinary runtime selection/planning failures remain valid behavior, not editor validation errors. Revalidate persisted input and generated runtime definitions on load; localStorage is not inherently trusted.
- **Resource bounds:** centralize and test finite project byte/block/depth limits, tactic/parameter/call-depth limits, finite retries and numeric arguments, bounded source sets, bounded forecasting and per-decision capability/command budgets. Count and bound the expanded runtime tree before materializing it; repeated acyclic calls must not bypass limits through exponential expansion. Proposed initial ceilings for the feasibility check are 256 KiB serialized input, 128 expanded executable nodes, depth 12, 8 retry attempts and 8 chosen sources; the capture horizon must also respect the agent's existing positive finite maximum of 60000 ms. Final admission limits are chosen from measured worst-case behavior in slice 1 and locked down before runtime integration. Invalid or over-budget programs must fail safely instead of stalling indefinitely; limits reject/stop execution rather than silently truncating chosen source sets or changing authored policy. A synchronous runtime cannot promise a hard wall-clock timeout; if acceptable responsiveness cannot be demonstrated with these bounds, narrower limits or an isolated runtime become a prerequisite to normal release.
- **Fault handling:** distinguish expected FAILED tree results from unexpected compiler/runtime faults. On an unexpected fault, stop that custom runtime, perform memory cleanup and show a readable fault state; do not silently start utility AI or run both controllers. Already accepted game orders retain normal game semantics. Do not describe method allowlisting or a worker as a security sandbox.
- **Saving:** Save validates and writes only that enemy's project. Invalid edits never overwrite its last valid saved project. Report unavailable/full storage and preserve the working draft; do not claim success after a swallowed storage error. Reset loads the bundled default into the draft and requires Save to replace the saved custom project. Choosing Normal disables custom execution but does not delete its project. Leaving with changes offers discard or cancel; no autosave is required.
- **Match snapshots:** only a newly started match receives newly saved logic. Capture a validated, immutable runtime-program snapshot per custom enemy in round setup and saved-game data, independent of mutable editor projects. Restart/Play again reuse that snapshot; editing/resetting/deleting a project later cannot change a restored match's strategy. Old saves without custom-program metadata keep existing behavior. Corrupt/unsupported custom snapshots must produce explicit recovery rather than silently substituting a bot or discarding editor data. No Blockly editor workspace is required on the gameplay execution path.
- **Lifecycle:** one persistent tree/agent per custom faction. Skip utility-worker and synchronous-utility decisions only for custom-controlled factions; normal factions continue unchanged. Pause/hidden time freezes stepping and scheduled waves. Restart/Home/disposal clear runtime memory; reload restores the frozen program but starts fresh tree/plan memory and excludes existing busy sources/committed targets as today. Unissued waves are not resumed. Explicit custom programs must not be overwritten by the development URL's bundled default, and no flag/configuration combination may double-control a faction.
- **Loading and offline use:** load the editor lazily so a normal game does not eagerly initialize Blockly. Pin the tested dependency and retain required license notices. Make offline availability an explicit tested PWA behavior; opening the editor for the first time offline must either work from precached assets or explain its unavailable state without damaging drafts. Do not assume a previously unvisited lazy chunk is cached.
- **Acceptance:** edit the shared Capture tactic's source limit or Main's neutral/enemy priority, save it, start a match with that custom enemy from normal Home settings, and observe the authored difference without a URL flag. Verify both Capture(kind) calls bind their own target kind and private slots, a shared-definition edit affects both on recompilation, nested parameter forwarding works, and malformed/recursive call graphs cannot activate. Also demonstrate a real capture requiring two sources, unchanged default AI for another faction, no duplicate orders, pause/reload/replay consistency, invalid-project rejection and recovery from storage/runtime errors. Verify narrow phone and desktop interaction, keyboard essentials and Blockly mount/disposal without leaked listeners/workspaces.

## Assumptions
- Reusable tactics with typed input parameters and ordinary Home activation are confirmed requirements, not deferred scope. The bounded scalar-input/no-recursion model above keeps this MVP smaller than a general-purpose language.
- Normal production release remains gated on validation, resource-bound, lifecycle and user-led design evidence; confirmation of Home availability does not waive these checks.
- Projects are local and independent per enemy, not shared by reference between enemies. The default custom project reproduces the current neutral-first capture strategy and uses the same troop accounting and faction decision intervals.
- Save is explicit and changes apply to new matches only. Runtime program snapshots, not mutable editor references, are necessary to preserve current replay/restore expectations.
- Blockly/Zelos is the preferred library based on primary-source research. Actual phone usability and bundle/runtime cost remain to be checked; the handwritten mockup is not that evidence.
- The existing production PWA suite has a separately reproduced 320px header-overlap blocker. Record that baseline separately; it does not authorize weakening tests or claiming new editor/offline tests pass without running them.

## Implementation Plan
### 1. Blockly Feasibility and Design
Description: Build an isolated Blockly-backed revision under mockups using the shared mockup workspace, custom nested blocks, inline fields, Main/Capture tabs and parameterized calls. Demonstrate editing a shared definition and distinct neutral/enemy arguments; compare Zelos interaction with the current design and exercise touch/keyboard alternatives with the user. Measure representative worst-allowed project/forecast costs and propose enforceable limits; identify any runtime-isolation prerequisite before normal release. Verify serving and obtain explicit design approval; no production code changes in this slice. Preserve approved sources and verify/stop the owned server before slice 2.

### 2. Project Format and Blocks
Description: After slice 1 approval, define the versioned project envelope, dependency/version boundary, typed fields and the bounded MVP block catalog, including visible cleanup, procedure models, definition/parameter identities and the default Main/Capture workspaces. Provide headless serialization fixtures and deterministic workspace/model load/save behavior; no game activation yet. Verify round-trip preservation of IDs, signatures, call arguments, fields/order, primitive slot kinds, default-project completeness, unsupported versions and malformed input.

### 3. Validation and JSON Compiler
Description: Using slice 2's blocks, implement pure validation and compilation to Mistreevous JSON with block-linked diagnostics, measured resource admission limits and method allowlists. Extend the persistent runtime to accept native definitions and enforce execution budgets/fault handling without changing tactical policy. Verify direct-tree fixture equivalence to the existing capture behavior, expected failures versus faults, retry/cleanup/RUNNING semantics, invalid connections/slots/numbers, oversized programs and single/multi-source real simulations. No editor persistence or Home activation yet. This slice first verifies direct trees; reusable call expansion follows in slice 4.

### 4. Parameterized Tactics and Scoped Compilation
Description: Using slices 2 and 3, validate the tactic call graph and compile calls through bounded expansion, typed literal/forwarded argument binding and deterministic per-call local memory. Seed Main with Capture(neutral) and Capture(enemy), preserving ordinary behavior-tree statuses and correctly bound cleanup. Verify two call sites cannot share target/source/plan slots, nested forwarding, RUNNING persistence, repeated invocation cleanup, shared-definition edits, rename/reference round trips, invalid signature changes, missing references, direct/indirect recursion and expanded-size/depth limits. Use real capture simulations, not only generated JSON snapshots; no game-settings activation yet.

### 5. Editor and Local Drafts
Description: Build the approved responsive editing screen with the block library, Main/tactic tabs, create/rename/delete and parameter-signature controls, inline call arguments, essential keyboard/touch operations, undo/redo, errors, explicit Save, Reset and unsaved-change handling. Store one validated project per enemy with reported storage failures and protected last-valid data. Add the Home Edit logic entry and Normal/Custom choice, keeping activation feature-gated until slice 6 is complete rather than presenting a selection that silently runs a different bot. Verify edit/save/reopen fidelity, draft isolation, narrow/wide layout, invalid Save, reset/discard behavior, storage/version recovery and Blockly disposal. Lazy-load the editor and retain license notices.

### 6. Per-enemy Game Integration
Description: Activate validated custom programs at new-match creation, freezing runtime JSON per faction into round setup and saved-game data. Keep normal AI running only for normal factions, preserve the development prototype's compatibility without double control, and restore/replay the same frozen program with fresh runtime memory. Verify changed branch priority/source limits in real gameplay, the two-source capture case, mixed normal/custom enemies, exactly-once dispatch, pause/hidden time, Home/restart, project edits after match creation, legacy saves, corrupted snapshots and explicit runtime-fault recovery. Normal release remains blocked if slice 1's safety/performance gate is not met.

### 7. Handover and Regression Checks
Description: Add concise usage/contracts/recovery documentation and automated end-to-end coverage of edit → save → start → observe behavior. Run unit tests, focused editor/gameplay browser tests, TypeScript/production build and applicable standard/PWA regressions, including lazy editor assets offline. Distinguish pre-existing PWA failures from editor regressions and leave blocked checks explicit. Complete user-led phone/desktop/keyboard acceptance and record any real-device/performance limitations; do not claim human review from HTTP checks or unit tests.
